Nothing here has been run. Each block needs **Abram's explicit OK** and the stated isolation before anyone runs it. The offline suite (`npm test`) already covers logic with fakes. These checks cover what fakes cannot prove: real Google semantics, real DDL, and the real deployed wiring.

## A. Google Calendar contract checks (disposable, isolated calendar ONLY)
**Isolation:** create a NEW secondary calendar (e.g. `bbs-phaseA-sandbox`) under the business account. Never use `primary`. Every call uses `sendUpdates=none` and **no attendees**, so no one is invited or emailed. Delete the calendar afterwards.

Setup (operator shell, token from the existing refresh-token flow; never paste it into chat):
```bash
CAL="<sandbox calendar id>"; T="<access token>"   # the same id goes into GOOGLE_CALENDAR_ID for §C
API="https://www.googleapis.com/calendar/v3/calendars/$CAL/events"
ID="bbs$(uuidgen | tr -d - | tr A-Z a-z)"
body='{"id":"'"$ID"'","summary":"sandbox","start":{"date":"2030-01-01"},"end":{"date":"2030-01-02"}}'
```
| # | Check | Command sketch | Expected (R7 design depends on it) |
|---|---|---|---|
| G1 | insert with explicit id | `curl -sX POST "$API?sendUpdates=none" -H "Authorization: Bearer $T" -H 'Content-Type: application/json' -d "$body"` | 200, `id == $ID`, has `etag`, no `attendees` |
| G2 | re-insert same id | same as G1 | **409** |
| G3 | GET returns etag | `curl -s "$API/$ID" -H "Authorization: Bearer $T"` → save `E1` | `etag` present |
| G4 | stale If-Match refused | PATCH summary with `If-Match: E1` (succeeds, new etag E2), then PATCH again with `If-Match: E1` | 2nd → **412**, event unchanged |
| G5 | delete, then re-insert same id | `DELETE $API/$ID?sendUpdates=none` then G1 again | DELETE 204, re-insert usually **409** (informational; the design does not rely on it) |
| G6 | cancelled event still readable | GET after G5 | 200, `status:"cancelled"` |
| G7 | delete again | DELETE after G5 | **410** |
| G8 | fence moves the etag of an already-cancelled event | GET → `Ec`; PATCH `{"status":"cancelled","extendedProperties":{"private":{"bbs_fence":"n1"}}}` | 200, new etag ≠ `Ec`; status still cancelled |
| G9 | stale restore after fence refused | PATCH `{"status":"confirmed"}` with `If-Match: Ec` | **412**, stays cancelled |
| G10 | private props merged, not replaced | first set `private.other=keep`, then G8 with a new nonce | `other` still present |
| G11 | same-value PATCH (informational) | PATCH `{"status":"cancelled"}` without fence; compare etags | record the result; the design does NOT rely on it |
| G12 | all-day exclusive end / 11:30 PM rollover | insert bodies generated by `lib/google-calendar.js` (`__test.parseBookingDateTime`) | accepted; displays on the right day |
| G13 | restore with fresh etag | GET cancelled → PATCH `{"status":"confirmed"}` with current etag | 200 confirmed (the legit-restore path works) |

**If G4, G8 or G9 differs from the expected result, the conditional-write fencing is not valid: launch is blocked.** G2/G5 are informational only. Google documents that id collisions may go undetected at creation time, so a 409 in the sandbox does not prove that an uncertain insert can never land (runbook §9).

## B. SQL up/down verification (disposable DB ONLY: a Supabase branch or local Postgres ≥ 11 with a schema-only copy of `bookings`)
```bash
pg_dump --schema-only -t public.bookings "$PROD_RO_URL" > bookings_schema.sql   # read-only, schema only, no rows
psql "$SANDBOX_URL" -f bookings_schema.sql
psql "$SANDBOX_URL" -c "insert into public.bookings (customer_email,status) values ('a@example.invalid','pending'),('b@example.invalid','contacted');"
psql "$SANDBOX_URL" -v ON_ERROR_STOP=1 -f migrations/20260923_booking_calendar_sync.up.sql
psql "$SANDBOX_URL" -c "select calendar_sync_status, revision, ownership_proof, calendar_event_proof, calendar_op_started_at from bookings;"
#   expect: unknown | 0 | null | null | null for every row
psql "$SANDBOX_URL" -v ON_ERROR_STOP=1 -f migrations/20260923_booking_calendar_sync.up.sql   # idempotent re-run: no error
psql "$SANDBOX_URL" -c "update bookings set calendar_sync_status='bogus';"                   # expect CHECK violation
psql "$SANDBOX_URL" -v ON_ERROR_STOP=1 -f migrations/20260923_booking_calendar_sync.down.sql
psql "$SANDBOX_URL" -c "\\d public.bookings"   # 7 columns gone, all original columns + rows intact
```

## C. Isolated preview checks (Vercel preview, NOT production; test data only)
Preconditions (all mandatory; stop if any is missing):
- `GOOGLE_CALENDAR_ID` set **explicitly** on the preview environment to the disposable sandbox calendar id from §A (never unset: unset means `primary`, the production calendar). Before any booking test, confirm with one read-only call that the id resolves to the sandbox calendar's summary.
- Preview-scoped Supabase URL + service-role key for a **sandbox** project, not inherited from production.
- **No production send credentials inherited:** leave the Brevo key and Telegram bot token/chat id unset on the preview environment (the code skips sending without them), or point them at a test inbox/chat. Check the preview env list before deploying.
- `BOOKING_STORE_MODE=full`; `BOOKING_OWNERSHIP_SECRET` set (a preview-only value, not the production secret).
1. **Function budget:** read the actual `maxDuration` / Fluid Compute setting for the booking routes (parent is checking the Vercel config read-only). Confirm the worst case (sync 4.5 s + record 1 s + notify 2.5 s + identify 1 s ≈ 9 s, plus DB/parse/network headroom, plus the R7 extra GET/fence calls) fits. If the limit is 10 s, lower `BOOKING_TIMEOUT_SYNC_MS` so there are ≥2 s of headroom.
2. **Create:** submit the free-measurement form → 200, sandbox event created, customer page shows success, the response `calendarSync` is `{status}` only.
3. **Customer reschedule / cancel** via `/booking/view?token=…` → same event moved / deleted + fenced. The lookup response has no calendar ids or notes.
4. **Forged row:** insert a row directly with the anon key (must now FAIL after the policy drop). With the service role, insert a row with no proof and an existing sandbox event id → customer cancel leaves that event untouched, CRM shows "not verified".
5. **CRM:** red badge + Retry on failure, amber + Retry for pending/unknown (full mode), Verify button on unverified rows, and follow-up ✅ Done leaves `bookings.status` unchanged.
6. **Analytics:** with a blocked/throwing gtag, a booking still shows success (R3). Use a hydrated browser (Playwright from the workspace `.venv`), not curl.
7. **No-service-role:** preview without `SUPABASE_SERVICE_ROLE_KEY` → booking APIs answer 503 (never the anon fallback).
